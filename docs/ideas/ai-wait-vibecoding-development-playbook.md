# AI 等待即时游戏助手：Vibe Coding 开发流程与提示词手册

本手册把传统的产品、设计、研发流程压缩为单人 + AI 可执行的流程。原则是：**一次只让 AI 完成一个可验证的任务；先验证闭环，再增加功能。**

## 0. 使用方式

### 每次新会话先提供的上下文包

不要把所有聊天记录粘给 AI。每次开始一个新阶段时，发送以下提示词，并让 AI 自己读取相关文档：

```text
项目目录：<你的项目绝对路径>

你是本项目的实现负责人。开始前必须读取：
1. docs/ideas/ai-wait-instant-game-assistant-prd.md
2. docs/ideas/ai-wait-mvp-cross-functional-review.md
3. AGENTS.md（若存在）

当前任务：<粘贴本阶段任务>

工作规则：
- 只实现当前任务，不顺手扩展 P1/P2 功能。
- 修改前先检查现有文件、依赖和类似实现；不要臆造 API。
- 先用不超过 6 条说明实现计划，再开始修改。
- 不接入未获得权利确认的第三方游戏、广告、商家福利或云游戏。
- 不读取、上传或记录用户的提示词、代码和模型输出。
- 完成后运行最相关的检查，并报告修改文件、验证结果和遗留风险。
- 如需求与现有代码冲突，停止并清楚说明冲突，不要擅自决定。
```

### 当前 MVP 不可越过的边界

- Alpha 只做 Windows Chrome 浏览器扩展、手动等待模式、3 款权利清晰的网页游戏和可靠回归；
- 不做账号、广告、奖励、商家后台、积分、云试玩、自研游戏或自动点击；
- AI 自动状态识别属于 Beta，必须先通过独立 PoC；
- 没有明确许可证或书面授权的游戏一律不上架。

## 1. 建立项目规则与技术骨架

### 目标

让后续 AI 会话都能知道项目边界、技术选型、命令和禁止项，避免每次重新解释需求。

### 交付物

- `AGENTS.md`；
- 技术选型说明；
- 空项目的目录结构；
- 不含功能代码的初始化提交点或可回滚状态。

### 给 AI 的提示词

```text
当前任务：初始化 AI 等待即时游戏助手的项目规则与技术骨架。

请先读取 PRD 与跨职能评审记录。项目为空时，采用以下默认方案：
- Windows Chrome 扩展，Manifest V3；
- TypeScript + React；
- 选择一个维护良好的扩展开发脚手架，并说明选择原因；
- 本地设置使用浏览器扩展存储；
- 首版不需要服务端、数据库、登录或第三方分析服务。

执行要求：
1. 先输出不超过 6 条计划与拟使用的命令，等待我确认后再安装依赖。
2. 确认后创建 AGENTS.md，写清技术栈、命令、代码风格、隐私边界和 MVP 非目标。
3. 初始化可运行的最小扩展工程，但不要实现等待、游戏或自动识别功能。
4. 添加 README，说明本地启动、加载未打包扩展和构建命令。
5. 运行构建或类型检查并报告结果。
```

### 你要确认

- AI 选择的脚手架能生成 Chrome Manifest V3 扩展；
- 项目能在 Chrome 的“加载已解压的扩展程序”中被识别；
- `AGENTS.md` 明确写入不接入未授权游戏与不采集代码/提示词的规则。

## 2. 先做可点击的低保真原型

### 目标

在没有复杂扩展逻辑前，确认用户能理解整个闭环，并及早发现交互问题。

### 交付物

- 可本地打开的交互原型；
- 五个状态：扩展弹窗、等待推荐卡、游戏启动页、AI 完成通知、设置页；
- 原型验收清单。

### 给 AI 的提示词

```text
当前任务：在现有项目中实现低保真交互原型，不实现真实的浏览器扩展逻辑。

请用现有前端栈制作可点击原型，模拟以下完整流程：
1. 用户点击“开始等待”；
2. 模拟等待达到 90 秒后出现非阻断游戏推荐卡；
3. 用户选择“立即游玩”，进入一个占位游戏启动页；
4. 模拟 AI 完成，显示“回到 AI 任务”的通知；
5. 用户点击后回到原始任务状态。

要求：
- 使用 3 个虚构游戏占位条目，不引用或展示第三方游戏素材；
- 提供“跳过”“本次不提醒”“结束等待”和设置阈值的状态；
- 视觉上清楚区分原工作、游戏推荐与完成召回；
- 不添加登录、排行榜、积分、广告或复杂动画；
- 为关键交互补充最少的组件测试或手动验收步骤；
- 运行项目并说明如何查看原型。
```

### 你要测试

- 第一次看到原型的人是否知道游戏不会自动打开；
- 用户是否能在两次操作内找到“回到 AI 任务”；
- 推荐卡是否遮挡 AI 输入区或结果区；
- 用户是否觉得通知与游戏提示在抢注意力。

## 3. 开发手动等待模式 PoC

### 目标

验证最核心的技术闭环：浏览器扩展能开始等待、到时展示卡片、通知用户并聚焦原标签页。

### 交付物

- 可加载的 Chrome 扩展 PoC；
- 手动开始/结束等待；
- 90 秒阈值与本地可配置阈值；
- 浏览器通知与原标签页返回；
- PoC 测试报告。

### 给 AI 的提示词

```text
当前任务：实现 Alpha 的“手动等待模式”技术 PoC。

范围：
- 在扩展 Popup 中提供开始等待、结束等待、当前状态与阈值设置；
- 用户开始等待时记录当前活动标签页；
- 到达阈值后仅显示一张游戏推荐卡或扩展内提醒，不自动打开游戏；
- 用户结束等待时发送浏览器通知；用户点击“回到任务”后聚焦此前记录的标签页；
- 所有会话状态和设置保存在浏览器扩展本地存储；
- 支持浏览器 Service Worker 休眠后的恢复，不要依赖 Popup 常驻。

边界：
- 不注入任何 AI 页面状态识别逻辑；
- 不接入真实第三方游戏；用本地占位页面模拟“打开游戏”；
- 不上传任何数据、不添加后端。

请先检查所用扩展框架对定时器、通知和标签页聚焦的官方模式；不要假设 API 可用。实现后：
1. 增加关键逻辑的测试，或提供逐项可重复的手动测试脚本；
2. 运行类型检查和构建；
3. 列出 Chrome 中验证该 PoC 的准确步骤与已知限制。
```

### 你要亲自验证

1. 在任意网页点击“开始等待”，关闭 Popup 后计时仍然有效；
2. 修改阈值后新会话按新阈值运行；
3. 通知点击后回到正确的原网页，而不是游戏页或错误标签；
4. 刷新游戏页、关闭标签、关闭 Popup 等异常情况不会使扩展崩溃；
5. 扩展没有读取页面正文、表单输入或剪贴板。

## 4. 筛选并核验首发游戏内容

### 目标

在写正式游戏接入前，拿到 3 款能合法使用且体验合格的内容。

### 交付物

- `docs/content/game-rights-ledger.md`；
- 3 款通过的首发候选，另有备选；
- 每款游戏的许可、加载、退出与适龄检查结果。

### 给 AI 的提示词

```text
当前任务：为 Alpha 建立首发网页游戏的内容准入台账；不要下载、复制、重新托管或上线任何第三方游戏。

请创建 docs/content/game-rights-ledger.md，表格至少包括：
- 游戏名与来源链接；
- 许可证/书面授权证据链接；
- 是否允许网页分发、嵌入、修改和商业使用；
- 依赖与第三方素材的许可风险；
- 适龄和地区限制；
- Chrome 加载耗时、是否可暂停、是否可安全退出；
- 负责人、核验日期、结论（候选/通过/拒绝）。

仅把拥有明确可验证许可的内容标为“候选”。许可证不明确、仅允许个人游玩、需要注册或包含未经审核广告的内容必须标为“拒绝”。
请在文档底部写出：在人工确认权利前，任何候选都不得进入产品。
```

### 你要确认

- 不把“网上能打开”误当成“可以接入产品”；
- 首发游戏至少覆盖两种等待时长，例如 1–3 分钟和 5–10 分钟；
- 每款游戏都满足“打开快、可安全退出、没有未审核广告”。

## 5. 接入已通过的游戏目录

### 目标

让游戏推荐从占位数据变成仅包含已批准内容的、受控的体验。

### 交付物

- 本地游戏目录配置；
- 游戏卡片与启动页；
- 加载失败与退出的降级体验；
- 内容台账与配置的一一对应关系。

### 给 AI 的提示词

```text
当前任务：接入 game-rights-ledger.md 中人工标记为“通过”的游戏；如果台账没有任何通过条目，停止并只保留占位数据。

实现要求：
- 游戏目录只从一个类型安全的本地配置读取；
- 每个条目包含名称、来源、时长、标签、可暂停状态、权利记录引用和启动 URL；
- 卡片按已等待时间推荐：短等待优先短局内容，较长等待才显示沉浸内容；
- 在独立游戏标签页打开；不得把第三方页面直接注入 AI 页面；
- 加载失败时显示“返回任务”和“换一款”两个明确操作；
- 对未知 URL、缺失字段和未批准状态进行防御性处理；
- 不实现收藏、账号、推荐算法或任何商业功能。

完成后运行测试与构建，并报告哪些具体内容实际被接入。
```

## 6. 实现最小隐私与体验事件

### 目标

在不采集用户代码和对话的前提下，知道闭环是否真正有效。

### 交付物

- 事件定义文档；
- 本地事件队列或仅开发期调试面板；
- 分析开关与清除本地数据功能。

### 给 AI 的提示词

```text
当前任务：实现 Alpha 的最小体验事件与隐私控制。

只允许记录以下事件：wait_started、threshold_reached、card_shown、game_opened、game_load_failed、wait_ended、return_clicked、original_tab_focused、recommendation_disabled。

要求：
- 事件字段不得包含网页正文、URL 查询参数、提示词、代码、模型输出、账号标识或完整浏览历史；
- Alpha 默认只在本地保存事件，用于调试和用户导出；不接第三方统计 SDK 和后端；
- 设置页提供“启用匿名体验分析”和“清除本地数据”；
- 为事件字段添加类型定义与单元测试；
- 创建 docs/analytics/alpha-event-spec.md，列出每个事件的触发时机和允许字段。
```

## 7. 设计完善与可用性检查

### 目标

在功能稳定后完善视觉层级，而不是把设计工作变成无止境的装饰。

### 交付物

- 一套克制的组件样式；
- 空状态、加载失败、通知权限拒绝等状态；
- 可用性测试脚本与修复清单。

### 给 AI 的提示词

```text
当前任务：在不改变 Alpha 功能范围的前提下，完善扩展的视觉层级和异常状态。

设计目标：轻量、游戏感适度、绝不妨碍用户编码。请重点处理：
- Popup 的开始/结束等待状态；
- 页面内推荐卡不遮挡 AI 关键区域；
- 游戏卡清楚显示时长、可暂停状态与退出提示；
- 通知权限被拒绝、游戏加载失败、原始标签页已关闭、手动模式结束等异常状态；
- 键盘操作、焦点顺序、基础对比度与窄窗口布局。

不要增加品牌动效、排行榜、积分、广告位或新页面。完成后给出 10 分钟可用性测试脚本，并运行现有检查。
```

## 8. Beta 前自动状态识别 PoC

### 目标

仅在 Alpha 手动闭环被用户认可后，测试一个网页 AI 是否能稳定驱动自动等待模式。

### 交付物

- 候选 AI 页面评估表；
- 一个隔离的状态适配器；
- 受控测试结果和安全回退逻辑。

### 给 AI 的提示词

```text
当前任务：为“一个指定的网页 AI 编程入口”做自动等待状态识别 PoC。

开始前请先向我确认目标网站与我能提供的测试页面信息。确认后：
1. 只观察与 UI 状态相关的最少 DOM 信号；不得读取、存储或传输对话正文、提示词、代码和模型输出。
2. 将适配器设计为独立模块，输出仅限 generating、completed、needs_user、unknown。
3. 当状态不确定、DOM 结构变化或连续判定冲突时，停用自动模式并回退到手动等待模式；绝不猜测“已完成”。
4. 增加模拟 DOM 测试或可重复的手动测试矩阵，覆盖开始、停止、继续生成、报错、网络异常和页面刷新。
5. 报告识别覆盖、误报风险、维护成本和是否建议进入 Beta。

不要把此 PoC 与 Alpha 主流程强耦合，也不要在没有我确认目标网站前编写站点特定选择器。
```

## 9. Alpha 验收、试用与迭代

### 目标

验证真实用户会不会使用，而不是只验证“AI 生成的代码能跑”。

### 交付物

- Alpha 构建包；
- 手动测试记录；
- 试用反馈表；
- 按严重性排序的迭代清单。

### 给 AI 的提示词

```text
当前任务：为 Alpha 发布准备测试与反馈闭环。

请基于当前实现创建：
1. docs/testing/alpha-manual-test-plan.md：覆盖安装、开始/结束等待、阈值、推荐卡、游戏启动、通知、返回、关闭标签页、权限拒绝、清除数据与卸载；
2. docs/testing/alpha-feedback-form.md：用不超过 10 个问题评估是否愿意使用、是否被打扰、是否及时回到 AI、哪类游戏适合等待；
3. 一个按 P0/P1/P2 严重性分类的缺陷模板；
4. 发布前检查清单：构建、权限说明、内容台账、隐私说明、已知限制。

不要添加新功能。运行已有自动化检查，并报告哪些只能由人工在 Chrome 中验证。
```

### 发布判断

只有同时满足以下条件，才让更多用户安装 Alpha：

- 3 款内容的权利记录完整；
- 手动等待、通知与返回在目标 Chrome 环境中可重复运行；
- 用户能关闭推荐和清除本地数据；
- 试用者没有反馈严重的“错过 AI 完成”问题；
- 未发现读取 AI 对话或代码的行为。

## 10. 每轮迭代的固定提示词

用这一条处理测试失败或用户反馈，避免 AI 趁机大改架构：

```text
当前任务：修复一个已确认的问题，不扩展功能范围。

问题现象：<粘贴一条错误或一个用户反馈>
复现步骤：<粘贴最短复现路径>
相关文件/日志：<只粘贴必要部分>

请按以下顺序执行：
1. 阅读相关实现与现有测试，说明最可能的根因；
2. 提出最小修复计划；
3. 实现修复并添加或更新针对性测试；
4. 运行相关检查；
5. 说明修复内容、验证证据和仍未覆盖的边界。

不要重构无关模块，不要新增依赖，不要改变 PRD 的 MVP 边界。
```

## 开发顺序总览

```text
规则与工程骨架
  → 交互原型
  → 手动等待 PoC
  → 内容权利台账
  → 接入 3 款通过游戏
  → 隐私与事件
  → 设计完善
  → Alpha 试用
  → 自动状态识别 PoC（Beta 闸门）
```

每完成一个箭头前的交付物，都应先测试和确认，再把下一个提示词交给 AI。这样仍然是 Vibe Coding，但不会把错误、版权风险或产品范围失控一起自动化。
